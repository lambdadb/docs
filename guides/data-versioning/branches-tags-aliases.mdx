LambdaDB data versioning provides named histories for the data stored in a collection. Every collection starts with a default branch named `main`.

| Ref type | Purpose | Writable | Target can change |
|:----|:--------|:---------|:------------------|
| Branch | Isolated line of document history | Yes | Advances when writes commit |
| Tag | Immutable name for one committed snapshot | No | No |
| Alias | Stable read name for a branch or tag | No | Yes, with `PATCH` |

Refs are scoped to one collection. Branch merge, direct branch reset, ref rename, and cross-collection snapshot sharing are not part of this API. Branch, tag, and alias names must contain 3 to 52 letters, numbers, underscores, or hyphens.

## Use the SDKs

Install a [supported SDK version](/reference/sdk/introduction#data-versioning-support) and use your project's connection details from LambdaDB Cloud. These examples assume an existing `knowledge-base` collection with a `title` text field and no branch named `candidate`. Run one language example or the REST alternative below, not both against the same branch name. The Go function accepts a client configured as shown in the [Start with an SDK](/guides/get-started/quickstart).

<CodeGroup>

```python Python
from lambdadb import BranchSource, LambdaDB, Ref

with LambdaDB(
    project_api_key="YOUR_API_KEY",
    base_url="YOUR_BASE_URL",
    project_name="YOUR_PROJECT_NAME",
) as client:
    collection = client.collection("knowledge-base")
    branch = collection.branches.create(
        "candidate", source=BranchSource.branch("main")
    ).branch
    if branch.parent_branch is not None:
        print(branch.parent_branch.name)
    if branch.head_snapshot is not None:
        print(branch.head_snapshot.snapshot_id)

    collection.docs.upsert(
        docs=[{"id": "doc-1", "title": "Candidate document"}], branch="candidate"
    )
    result = collection.docs.fetch(
        ids=["doc-1"], ref=Ref.branch("candidate"), consistent_read=True
    )
```

```typescript TypeScript
import { LambdaDBClient, branchRef, branchSource } from "@functional-systems/lambdadb";

if (branch.headSnapshot !== null) console.log(branch.headSnapshot.snapshotId);

```

```go Go
import (
    "context"
    "fmt"

    lambdadb "github.com/lambdadb/go-lambdadb"
)

func versioningExample(ctx context.Context, client *lambdadb.Client) error {
    collection := client.Collection("knowledge-base")
    branch, err := collection.Branches().Create(ctx, lambdadb.CreateBranchInput{
        BranchName: "candidate",
        Source:     lambdadb.BranchSource("main"),
    })
    if err != nil {
        return err
    }
    if branch.ParentBranch != nil {
        fmt.Println(branch.ParentBranch.Name)
    }
    if branch.HeadSnapshot != nil {
        fmt.Println(branch.HeadSnapshot.SnapshotID)
    }

    _, err = collection.Docs().Upsert(ctx, lambdadb.UpsertDocsInput{
        Docs:   []map[string]interface{}{{"id": "doc-1", "title": "Candidate document"}},
        Branch: lambdadb.String("candidate"),
    })
    if err != nil {
        return err
    }
    _, err = collection.Docs().Fetch(ctx, lambdadb.FetchDocsInput{
        Ids:            []string{"doc-1"},
        Ref:            lambdadb.BranchRef("candidate"),
        ConsistentRead: lambdadb.Bool(true),
    })
    return err
}
```

## Create and list branches

Create a branch from `main`:

```bash
curl -i -X POST \
  "$BASE_URL/projects/$PROJECT_NAME/collections/$COLLECTION_NAME/branches" \
  -H "content-type: application/json" \
  -H "x-api-key: $LAMBDADB_PROJECT_API_KEY" \
  -d '{
    "branchName": "candidate",
    "source": { "kind": "branch", "name": "main" }
  }'
```

Omit `source` to use `main`. A branch can be created from another branch or from a tag in the same collection; an alias source returns `400 BadRequest`. A branch created from an empty source branch has explicitly `null` `headSnapshot` and `parentSnapshot`, but `parentBranch` still identifies the source branch.

Without `source.asOf`, the new branch starts from the source's committed snapshot and also takes over the writes that were still pending on the source at creation time. Those writes are not part of its snapshot yet: ordinary reads of the new branch see them after its own build commits them, and a [consistent read](#consistent-reads) on the branch includes the eligible ones immediately. Writes that reach the source afterward do not appear on the new branch.

The new branch also inherits its source's index schema and owns it from then on; see [Branch index schemas](#branch-index-schemas). Retention remains collection-scoped.

```json
{
  "branch": {
    "name": "candidate",
    "parentBranch": {
      "branchId": "<main-branch-id>",
      "name": "main"
    },
    "headSnapshot": {
      "snapshotId": "<snapshot-id>",
      "snapshotCommittedAt": 1788335940000
    },
    "parentSnapshot": {
      "snapshotId": "<snapshot-id>",
      "snapshotCommittedAt": 1788335940000
    },
    "indexConfigs": {
      "title": { "type": "text" },
      "id": { "type": "keyword" }
    },
    "numDocs": 1250,
    "dataUpdatedAt": 1788335940000,
    "createdAt": 1788336000000
  }
}
```

### Create a branch from a tag

Set `source.kind` to `tag` to start a writable branch from a tag:

```json
{
  "branchName": "hotfix",
  "source": { "kind": "tag", "name": "validated-2026-09" }
}
```

The branch inherits the tag's snapshot, its pinned index schema, and the writes the tag captured when it was created. Writes made to the tag's original branch after the tag was created are excluded. `parentBranch` is `null` for a branch created from a tag, and `parentSnapshot` is the tag's snapshot at creation. `source.asOf` is not allowed with a tag source.

### List and describe branches

List branches:

```bash
curl -i \
  "$BASE_URL/projects/$PROJECT_NAME/collections/$COLLECTION_NAME/branches" \
  -H "x-api-key: $LAMBDADB_PROJECT_API_KEY"
```

The response contains a `branches` array, one page at a time in name order; see [Page through ref lists](#page-through-ref-lists). Each entry has the same fields as the create response. Read one branch with `GET .../branches/{branchName}`, which wraps the same object in `branch`; a name that is not a branch returns `404`.

| Field | Meaning |
| :---- | :------ |
| `parentBranch` | Fixed direct source branch at creation time, with `branchId` and `name`. Explicitly `null` for `main`, for a branch created from a tag, or when no parent was recorded. |
| `headSnapshot` | Current committed head, or `null` before a committed head exists. |
| `parentSnapshot` | Fixed snapshot from which the branch was created, not the previous head. `null` for `main` and branches created from an empty source, even after their first commit. |
| `snapshotCommittedAt` | Snapshot commit time in Unix epoch milliseconds, inside each non-null snapshot object alongside `snapshotId`. |
| `indexConfigs` | The branch's own index schema. |
| `numDocs` | Document count in the branch's committed head; `0` for an empty branch. |
| `dataUpdatedAt` | Last data update of the committed head in Unix epoch milliseconds; `null` for an empty branch. |
| `createdAt` | Branch creation time in Unix epoch milliseconds, independent of snapshot commit times. |

When created from a nonempty source, a branch initially has matching head and parent snapshots. The head can advance while the parent stays fixed. Parent metadata does not guarantee that the original snapshot remains available beyond retention. Branch responses do not have a top-level `snapshotId`.

`parentBranch` records the requested source branch, not the branch where the selected snapshot originated. For example, a branch created from `dev` records `dev` even if its snapshot originated on `main`, including when selected through `asOf`. This historical metadata does not prevent deleting the parent branch. Deleting the parent or recreating its name does not change the recorded identity.

## Branch index schemas

A branch owns its index schema. It inherits the schema when it is created: the source branch's current schema, the tag's pinned schema, or, with `source.asOf`, the schema of the selected snapshot. After that, a schema update changes only the branch it targets. Updating another branch, including `main`, does not change it.

Add fields to one branch with `PATCH .../branches/{branchName}`. The body takes `indexConfigs` only:

```bash
curl -i -X PATCH \
  "$BASE_URL/projects/$PROJECT_NAME/collections/$COLLECTION_NAME/branches/candidate" \
  -H "content-type: application/json" \
  -H "x-api-key: $LAMBDADB_PROJECT_API_KEY" \
  -d '{
    "indexConfigs": {
      "title": { "type": "text" },
      "category": { "type": "keyword" }
    }
  }'
```

The response is the updated `branch` object. The same additive rules as a [collection schema update](/guides/collections/manage-collections#update-the-index-schema) apply within the branch: send the branch's complete existing schema, preserve every existing field and its settings, and add new fields at any depth. A field's `description` is the only existing setting that can change. Concurrent additive updates of the same branch are merged.

- Updating `main` this way also updates the `indexConfigs` shown on the collection, which mirror `main`.
- Only a branch can be updated. Naming a tag or an alias returns `400 BadRequest`; a name that does not exist returns `404`.
- To bring a schema change from a branch to `main`, apply the same additive change to `main`. There is no automatic promotion.
- An alias can be retargeted between branches whose schemas differ; the server does not check it. Read the alias with `GET .../aliases/{aliasName}` to see which schema its readers currently get.

## Point-in-time branches

Set `source.asOf` to select the latest committed snapshot at or before that Unix epoch-millisecond timestamp:

```json
{
  "branchName": "recovery-check",
  "source": {
    "kind": "branch",
    "name": "main",
    "asOf": 1788336000000
  }
}
```

`asOf` is valid only when `source.kind` is `branch`. Missing or no-longer-retained history returns `400 BadRequest`. It selects committed history, so it cannot recover a write that was still pending at the requested time. There is no public snapshot-history-list API.

Pass a cutoff within your collection's retained history. The new `recovery-check` branch must not already exist. Python takes epoch milliseconds; TypeScript accepts a `Date`, and Go accepts `time.Time` through its source helper:

<CodeGroup>

```python Python
from lambdadb import BranchSource

def create_historical_branch(client, cutoff_ms: int):
    return client.collection("knowledge-base").branches.create(
        "recovery-check", source=BranchSource.branch("main", as_of=cutoff_ms)
    )
```

```typescript TypeScript
import { LambdaDBClient, branchSource } from "@functional-systems/lambdadb";

async function createHistoricalBranch(client: LambdaDBClient, cutoff: Date) {
  return client.collection("knowledge-base").branches.create({
    branchName: "recovery-check",
    source: branchSource("main", cutoff),
  });
}
```

```go Go
import (
    "context"
    "time"

    lambdadb "github.com/lambdadb/go-lambdadb"
)

func createHistoricalBranch(ctx context.Context, client *lambdadb.Client, cutoff time.Time) error {
    _, err := client.Collection("knowledge-base").Branches().Create(ctx, lambdadb.CreateBranchInput{
        BranchName: "recovery-check",
        Source:     lambdadb.BranchSourceAt("main", cutoff),
    })
    return err
}
```

## Create and list tags

A tag is a fixed, read-only name for the state of its source at creation. It cannot be retargeted:

```bash
curl -i -X POST \
  "$BASE_URL/projects/$PROJECT_NAME/collections/$COLLECTION_NAME/tags" \
  -H "content-type: application/json" \
  -H "x-api-key: $LAMBDADB_PROJECT_API_KEY" \
  -d '{
    "tagName": "validated-2026-09",
    "source": { "kind": "branch", "name": "candidate" }
  }'
```

Omit `source` to tag the current state of `main`. The create response wraps the ref in `tag`; `GET .../tags` returns a `tags` array one page at a time (see [Page through ref lists](#page-through-ref-lists)), and `GET .../tags/{tagName}` returns one `tag`. A name that is not a tag returns `404`.

A tag source can be a branch or another tag in the same collection, but not an alias. Creating a tag from a tag copies the same fixed state; it does not create a chain of tags. `source.asOf` is allowed only for a branch source.

Without `source.asOf`, a tag pins the source's committed snapshot together with the writes that were still pending on the source at that moment. Query and fetch reads of the tag include those captured writes, except pending bulk imports, which appear after a background build materializes them. Document listing shows captured writes once a background build has published them into the tag's snapshot. With `source.asOf`, the tag pins only the selected committed snapshot. A tag never accepts writes, and its captured state does not change when the source moves on.

As long as the tag exists, its pinned snapshot remains available even beyond the collection's [snapshot retention period](/guides/collections/create-a-collection#snapshot-retention). For example, with a 30-day retention period, a tagged snapshot remains readable through the tag after 30 days. This makes tags suitable for long-term savepoints, such as a data version associated with a code release. The tag preserves that snapshot, not all earlier snapshots.

Tag responses contain `name`, `snapshotId`, `snapshotCommittedAt`, `indexConfigs`, `numDocs`, `dataUpdatedAt`, and `createdAt`. Unlike branch responses, the snapshot fields are at the top level of the tag object. `snapshotCommittedAt` is the pinned snapshot's commit time, while `createdAt` is the tag's creation time; both use Unix epoch milliseconds. `indexConfigs` is the schema the tag pins, and `numDocs` and `dataUpdatedAt` describe its pinned snapshot.

```json
{
  "tag": {
    "name": "validated-2026-09",
    "snapshotId": "<snapshot-id>",
    "snapshotCommittedAt": 1788335940000,
    "indexConfigs": {
      "title": { "type": "text" },
      "id": { "type": "keyword" }
    },
    "numDocs": 1250,
    "dataUpdatedAt": 1788335940000,
    "createdAt": 1788336060000
  }
}
```

A tag cannot be created from an empty head.

## Create, retarget, and list aliases

An alias points to a branch or tag:

```bash
curl -i -X POST \
  "$BASE_URL/projects/$PROJECT_NAME/collections/$COLLECTION_NAME/aliases" \
  -H "content-type: application/json" \
  -H "x-api-key: $LAMBDADB_PROJECT_API_KEY" \
  -d '{
    "aliasName": "production-read",
    "target": { "kind": "tag", "name": "validated-2026-09" }
  }'
```

Retarget it without changing the alias name used by readers:

```bash
curl -i -X PATCH \
  "$BASE_URL/projects/$PROJECT_NAME/collections/$COLLECTION_NAME/aliases/production-read" \
  -H "content-type: application/json" \
  -H "x-api-key: $LAMBDADB_PROJECT_API_KEY" \
  -d '{
    "target": { "kind": "branch", "name": "main" }
  }'
```

`GET .../aliases` returns an `aliases` array one page at a time (see [Page through ref lists](#page-through-ref-lists)), and `GET .../aliases/{aliasName}` returns one `alias`. Alias objects include `aliasId`, `aliasName`, `targetKind`, `targetName`, `targetId`, `aliasRevision`, `dangling`, `indexConfigs`, and epoch-millisecond `createdAt`. Request `kind` values are lowercase; response `targetKind` values are `BRANCH` or `TAG`.

`indexConfigs` on an alias is the schema its readers currently get: the target branch's current schema or the target tag's pinned schema. Create and retarget responses carry it too, so a retarget shows the schema the alias now serves.

```json
{
  "alias": {
    "aliasId": "<alias-id>",
    "aliasName": "production-read",
    "targetKind": "TAG",
    "targetName": "validated-2026-09",
    "targetId": "<tag-id>",
    "aliasRevision": 0,
    "dangling": false,
    "indexConfigs": {
      "title": { "type": "text" },
      "id": { "type": "keyword" }
    },
    "createdAt": 1788336120000
  }
}
```

Deleting a non-default branch or a tag that is referenced by any alias returns `409 Conflict`. Delete or retarget every referencing alias before deleting the target; retrying the same deletion without changing those references will not resolve the conflict. Deleting an alias does not delete its target.

Aliases bind to the target's identity, not just its name. The response retains a `dangling` field for a missing target; if such a state is encountered, document reads through the alias return `400 BadRequest`, while `GET .../aliases/{aliasName}` still returns the alias with `dangling: true` and `indexConfigs: null`. It is not the normal result of target deletion, which is blocked while aliases reference it. Recreating a target name does not repair the old identity binding. Selecting a ref that does not exist returns `404 ResourceNotFound`.

### Publish a tag through an alias with the SDKs

First verify that `candidate` contains the intended committed data using a fetch or query with `consistentRead: false`. The following example assumes that verification is complete and that neither `validated-2026-09` nor `production-read` exists. It pins a tag, creates an alias initially targeting `main`, switches that alias to the tag, and reads through the alias. For an existing alias, use only the retarget call instead of creating it again.

<CodeGroup>

```python Python
from lambdadb import AliasTarget, Ref, RefSource

def publish_tag(client):
    collection = client.collection("knowledge-base")
    collection.tags.create(
        "validated-2026-09", source=RefSource.branch("candidate")
    )
    collection.aliases.create("production-read", target=AliasTarget.branch("main"))
    collection.aliases.retarget(
        "production-read", target=AliasTarget.tag("validated-2026-09")
    )
    return collection.docs.fetch(ids=["doc-1"], ref=Ref.alias("production-read"))
```

```typescript TypeScript
import { LambdaDBClient, aliasRef, branchSource, branchTarget, tagTarget } from "@functional-systems/lambdadb";

async function publishTag(client: LambdaDBClient) {
  const collection = client.collection("knowledge-base");
  await collection.tags.create({
    tagName: "validated-2026-09", source: branchSource("candidate"),
  });
  await collection.aliases.create({
    aliasName: "production-read", target: branchTarget("main"),
  });
  await collection.aliases.retarget("production-read", {
    target: tagTarget("validated-2026-09"),
  });
  return collection.docs.fetch({ ids: ["doc-1"], ref: aliasRef("production-read") });
}
```

```go Go
import (
    "context"

    lambdadb "github.com/lambdadb/go-lambdadb"
)

func publishTag(ctx context.Context, client *lambdadb.Client) error {
    collection := client.Collection("knowledge-base")
    _, err := collection.Tags().Create(ctx, lambdadb.CreateTagInput{
        TagName: "validated-2026-09", Source: lambdadb.BranchSource("candidate"),
    })
    if err != nil {
        return err
    }
    _, err = collection.Aliases().Create(ctx, lambdadb.CreateAliasInput{
        AliasName: "production-read", Target: lambdadb.BranchTarget("main"),
    })
    if err != nil {
        return err
    }
    _, err = collection.Aliases().Retarget(ctx, "production-read", lambdadb.RetargetAliasInput{
        Target: lambdadb.TagTarget("validated-2026-09"),
    })
    if err != nil {
        return err
    }
    _, err = collection.Docs().Fetch(ctx, lambdadb.FetchDocsInput{
        Ids: []string{"doc-1"}, Ref: lambdadb.AliasRef("production-read"),
    })
    return err
}
```

## Page through ref lists

The branch, tag, and alias lists page the same way as the collection list. Each returns up to `size` entries in name order and, when more entries follow, a `nextPageToken`:

```bash
curl -i \
  "$BASE_URL/projects/$PROJECT_NAME/collections/$COLLECTION_NAME/branches?size=20" \
  -H "x-api-key: $LAMBDADB_PROJECT_API_KEY"

# Next page (use nextPageToken from the previous response)
curl -i \
  "$BASE_URL/projects/$PROJECT_NAME/collections/$COLLECTION_NAME/branches?size=20&pageToken=YOUR_PAGE_TOKEN" \
  -H "x-api-key: $LAMBDADB_PROJECT_API_KEY"
```

| Parameter | Description | Default |
| :-------- | :---------- | :------ |
| `size` | Entries per page, from 1 to 100. | 10 |
| `pageToken` | Opaque token from the previous page. Omit it for the first page. | |

`nextPageToken` is absent on the last page. Treat it as opaque and return it unchanged to the same list. An empty or malformed `pageToken`, a `size` outside the range, or any other query parameter returns `400 BadRequest`. A client that reads only the first response sees at most `size` entries, so follow `nextPageToken` until it is absent to see every ref.

## Read from a ref

Query, fetch, and extended list request bodies accept:

```json
{
  "ref": {
    "kind": "branch",
    "name": "candidate"
  }
}
```

`ref.kind` accepts `branch`, `tag`, or `alias`. Add this object alongside the endpoint's normal fields. Omitting `ref` reads from `main`.

The GET list endpoint has no request body. Supply `refKind` and `refName` together:

```bash
curl -i \
  "$BASE_URL/projects/$PROJECT_NAME/collections/$COLLECTION_NAME/docs?refKind=alias&refName=production-read" \
  -H "x-api-key: $LAMBDADB_PROJECT_API_KEY"
```

Supplying only one of `refKind` or `refName` is invalid.

### Consistent reads

Query and fetch requests support `consistentRead: true` when they select a branch directly or through an alias that currently targets a branch; the alias is resolved to its branch when the request is admitted. Tag reads and an alias that targets a tag reject it with `400`.

Consistent reads overlay eligible pending writes, including those a branch took over from its source at creation, on the branch's committed snapshot; ordinary branch reads use only the snapshot. Query and fetch reads of a tag already include the writes the tag captured, without the flag. They can return `429` when that pending payload reaches the [configured threshold](/guides/get-started/limits#search-and-reads), independently of request rate limits. Pending bulk imports are excluded and become visible only after indexing commits them. List requests do not support `consistentRead`: on every ref, document listing reads only the published snapshot.

Page tokens record a search position, not a fixed snapshot. Branches can advance and aliases can move between pages. Use the same immutable tag on every page for a stable export, keeping filters and projection options unchanged. Query responses do not include a resolved snapshot ID.

### Iterate over a tag with the SDKs

These examples assume `validated-2026-09` already exists. Each pagination helper keeps the same tag on subsequent requests. Python pages contain document dictionaries; TypeScript and Go pages contain result items whose `doc` or `Doc` field holds the document.

<CodeGroup>

```python Python
from lambdadb import Ref

def print_tag_documents(client):
    collection = client.collection("knowledge-base")
    for page in collection.docs.list_pages(size=100, ref=Ref.tag("validated-2026-09")):
        for document in page:
            print(document)
```

```typescript TypeScript
import { LambdaDBClient, tagRef } from "@functional-systems/lambdadb";

async function printTagDocuments(client: LambdaDBClient) {
  const collection = client.collection("knowledge-base");
  for await (const page of collection.docs.listPages({
    size: 100, ref: tagRef("validated-2026-09"),
  })) {
    for (const item of page.docs) console.log(item.doc);
  }
}
```

```go Go
import (
    "context"
    "fmt"

    lambdadb "github.com/lambdadb/go-lambdadb"
)

func printTagDocuments(ctx context.Context, client *lambdadb.Client) error {
    iterator := client.Collection("knowledge-base").Docs().ListIterator(ctx, &lambdadb.ListDocsOpts{
        Size: lambdadb.Int64(100), Ref: lambdadb.TagRef("validated-2026-09"),
    })
    for {
        page, err := iterator.Next(ctx)
        if err != nil {
            return err
        }
        if page == nil {
            return nil
        }
        for _, item := range page.Docs {
            fmt.Println(item.Doc)
        }
    }
}
```

## Write to a branch

Upsert, update, delete, and bulk-upsert request bodies accept an optional `branch` string. Omitting it writes to `main`.

```json
{
  "branch": "candidate",
  "docs": [
    { "id": "doc-1", "title": "Candidate document" }
  ]
}
```

The value is resolved as a branch name. A tag or alias is not a valid write target.

For bulk upsert, use the same branch for both control calls:

```text
GET  .../docs/bulk-upsert?branch=candidate
POST .../docs/bulk-upsert
{
  "objectKey": "...",
  "type": "application/json",
  "branch": "candidate"
}
```

Set `Content-Type` to the response's `type` value and send every entry in its `headers` map unchanged with the presigned `PUT`.

## Delete a ref

Delete a named ref with its type-specific route:

```text
DELETE .../branches/{branchName}
DELETE .../tags/{tagName}
DELETE .../aliases/{aliasName}
```

The default `main` branch cannot be deleted independently from its collection; an attempt returns `400 BadRequest`. Other branches and tags cannot be deleted while any alias references them (`409 Conflict`). Delete or retarget those aliases first. Deleting a ref does not delete the collection.

Deleting a tag removes its protection of the pinned snapshot; it does not immediately delete the snapshot. Once the snapshot is outside the retention period and no branch head or other tag references it, it becomes eligible for cleanup.

The default branch cannot be changed. Deleting an already absent ref can return `404`.
