Use `lambdadb` for project-scoped collection management, JSONL imports, queries, ID-based fetches, document updates and deletes, and branch, tag, and alias management. To transfer data from Qdrant, Pinecone, or Elasticsearch with inventory, mappings, and checkpoints, use the separate [Migration CLI](/guides/migrations/overview).

## Install

The stable release covered by this guide is `0.1.8`. Choose one installation method and check `command -v lambdadb` before switching package managers.

<Tabs>
  <Tab title="npm">
    Requires Node.js **22.14.0 or later** and npm.

    ```bash
    npm install --global @functional-systems/lambdadb-cli@0.1.8
    lambdadb --version
    lambdadb --help
    ```

    To update to the current stable channel:

    ```bash
    npm install --global @functional-systems/lambdadb-cli@latest
    ```

    To remove:

    ```bash
    npm uninstall --global @functional-systems/lambdadb-cli
    ```
  </Tab>
  <Tab title="Homebrew">
    On macOS or Linux with [Homebrew](https://brew.sh/):

    ```bash
    brew install lambdadb/tap/lambdadb-cli
    lambdadb --version
    lambdadb --help
    ```

    The public tap provides CLI `0.1.8` with its Node 24 runtime. No separate Node/npm setup is needed.

    ```bash
    brew update
    brew upgrade lambdadb/tap/lambdadb-cli
    ```

    To remove:

    ```bash
    brew uninstall lambdadb/tap/lambdadb-cli
    ```
  </Tab>
</Tabs>

Installed copies do not update themselves. Pin an exact version for reproducible npm installs; `@dev` is a separate prerelease channel. See [CLI releases](https://github.com/lambdadb/lambdadb-cli/releases) and the [public tap](https://github.com/lambdadb/homebrew-tap) for availability.

## Configure a project

<CloudConnectionDetails />

Use an existing development project and replace the placeholders below. The endpoint is your region's HTTPS API origin, without `/projects/...`. This `configure` flow uses an existing project and key.

```bash
lambdadb configure --endpoint YOUR_REGION_BASE_URL --project YOUR_PROJECT_NAME --api-key-env LAMBDADB_API_KEY
```

Supply the key through your shell or a CI secret manager. For example, in **Bash**, read it without putting the value in shell history:

```bash
read -r -s -p 'LambdaDB project API key: ' LAMBDADB_API_KEY
printf '\n'
export LAMBDADB_API_KEY
lambdadb doctor
```

This environment-variable setup saves the endpoint, project, and name of the key environment variable; `configure` makes no service call. Explicit `--api-key-env` selects environment mode even after an earlier `init` saved an OS credential reference. `doctor` checks authentication and collection-list access. Success does not prove write permission or search readiness.

Alternatively, `lambdadb init` uses browser-based account login, then project selection or creation and key issuance in the terminal. Account setup stores keys in the OS credential store and saves a non-secret reference in the CLI configuration. It can also register the connection with coding agents; see the [CLI setup guide](https://github.com/lambdadb/lambdadb-cli/blob/v0.1.8/docs/setup.md). Neither path creates documents or collections.

## Create a collection and import JSONL

The CLI supports all 49 [fixed text analyzer presets](/guides/collections/choose-text-analyzers).

For generated vectors, use the [native embedding configuration](/guides/collections/native-embeddings#collection-schema) in the same field-to-index map. The CLI also supports `lambdadb collections update --collection NAME --index-config FILE` with that map format. Existing field-update constraints still apply; see [Configure a collection](/guides/collections/manage-collections#configure-a-collection).

Choose a new collection name in your development project. Run these examples in a scratch directory. Create an index configuration file containing the field-to-index map, without an `indexConfigs` wrapper:

```bash
cat > index-config.json <<'JSON'
{
  "text": { "type": "text", "analyzers": ["english"] },
  "category": { "type": "keyword" }
}
JSON

lambdadb collections create --collection cli-demo-docs --index-config index-config.json
lambdadb collections describe --collection cli-demo-docs
```

Create and import a UTF-8 JSONL file:

```bash
cat > documents.jsonl <<'JSONL'
{"id":"doc-1","text":"LambdaDB supports serverless search.","category":"database"}
{"id":"doc-2","text":"Developers can search documents using a shared CLI.","category":"developer-tools"}
{"id":"doc-3","text":"A successful write is accepted before committed search visibility is verified.","category":"database"}
JSONL

lambdadb docs import --collection cli-demo-docs --branch main --file documents.jsonl --json
```

`--branch main` explicitly selects the writable branch. Import validates the entire file before sending sequential batches. Each nonblank line must be a JSON object; files are limited to 64 MiB and 100,000 documents. Existing IDs are upserted, so replay can replace data. Omitted IDs are generated by the service and are not returned in the acceptance response; replay can create duplicates.

<Note>
  Creation reports `state: "created"`; successful import reports `state: "accepted"`. Both report `searchable: "not_verified"`. Accepted writes are not proof that indexing has completed or documents are searchable. After a delay, repeat reads and inspect the expected IDs and contents. Do not recreate the collection or replay imports as a waiting mechanism.
</Note>

## Query and fetch by ID

Save a query request and select the read ref explicitly:

```bash
cat > query.json <<'JSON'
{
  "size": 10,
  "query": { "queryString": { "query": "serverless", "defaultField": "text" } },
  "consistentRead": false
}
JSON

lambdadb query --collection cli-demo-docs --ref branch:main --file query.json --json
lambdadb docs fetch --collection cli-demo-docs --ref branch:main --ids doc-1 doc-2 doc-3 --json
```

After indexing, the query should include `doc-1`, and fetch should return the three IDs. Initial reads can be empty or encounter a transient loading error. A successful empty result still exits with `0`; fetch includes `missingIds` for absent documents.

For eligible pending ordinary writes, fetch can use:

```bash
lambdadb docs fetch --collection cli-demo-docs --ref branch:main --ids doc-1 --consistent-read --json
```

For query, set `"consistentRead": true` in the request file. These reads require a direct branch ref, exclude pending bulk imports, and can return `429`. They do not establish committed indexing. See [Data versioning](/guides/data-versioning/branches-tags-aliases).

The CLI also accepts [keyword facets](/guides/search/facets) and an omitted `query` for match-all requests. Use `size: 0` with nonempty facets for counts without document results.

<a id="managed-reranking" />

### Native reranking

The CLI accepts the query-level `rerank` object through the same JSON request file. No separate reranking flags or provider API key are needed. Save this as `rerank-query.json` for the sample collection above:

```json
{
  "size": 2,
  "query": { "queryString": { "query": "serverless", "defaultField": "text" } },
  "rerank": {
    "provider": "typesafe",
    "model": "jev-1.13.0",
    "queryText": "Which documents explain serverless search?",
    "fields": ["text"]
  }
}
```

```bash
lambdadb query --collection cli-demo-docs --ref branch:main --file rerank-query.json --json
```

Read `data.rerank.status` in the CLI JSON envelope. On `applied` results, `data.docs` contains final evaluation `score` and original `retrievalScore` alongside each `doc`. Fallback retains search scores and server order with `scoredCount: 0`; it does not expose partial evaluation scores. The CLI preserves numeric zero and precision, including downloaded results, and does not sort again. See [Native reranking](/guides/search/native-reranking) for custom criteria, candidate depth, eligible `returnOriginal` failures, and query/sort/facet restrictions.

### Bayesian hybrid search

Save the complete [Bayesian request](/guides/search/hybrid#bayesian-hybrid-query) as `bayesian-query.json` and run it against a collection with the example's `body` and `bodyEmbedding` fields:

```bash
lambdadb query --collection semantic-docs --ref branch:main --file bayesian-query.json --json
```

Without reranking, supply top-level `candidateSize` with `1 <= size <= candidateSize <= 1000`. With reranking, omit that field and use `rerank.candidateSize`. No separate fusion flags are needed; existing search defaults are unchanged.

### Select collections and refs

- Endpoint and project come from configuration, environment, or flags. `--collection` is required for collection-specific operations.
- Import requires `--branch NAME`. Query and fetch require `--ref branch:NAME`, `--ref tag:NAME`, or `--ref alias:NAME`; the CLI does not silently select `main`.
- Tags and aliases must already exist; see [Branches, tags, and aliases](#branches-tags-and-aliases). Branches and aliases can move between calls.
- If a query file contains `ref`, it must match `--ref`. Query `size` is 1–1000 for document results; `size: 0` requires nonempty `facets` for counts only. Fetch accepts up to 1000 IDs.

## List, update, and delete documents

`docs list` pages through documents at a ref without ranking. `--size` accepts 1–100; use `--page-token` with the returned `nextPageToken`, or `--all` to follow pages to the end within the network budget. An optional `--file` holds `filter`, `partitionFilter`, and `fields`:

```bash
lambdadb docs list --collection cli-demo-docs --ref branch:main --size 5 --json

cat > list-filter.json <<'JSON'
{
  "filter": { "queryString": { "query": "category:database" } },
  "fields": { "include": ["id", "text", "category"] }
}
JSON

lambdadb docs list --collection cli-demo-docs --ref branch:main --file list-filter.json --json
```

Use a tag for a stable export; a branch can advance and an alias can be retargeted between pages. List does not support consistent reads, and `total` counts the page, not the collection.

`docs update` merges JSONL rows into existing documents. Every row needs a nonempty string `id` that already exists; omitted fields are kept, nested objects merge, arrays are replaced, and `null` is rejected for indexed fields. Batches run sequentially and stop at the first failure, with the same result fields and exit codes as import:

```bash
cat > updates.jsonl <<'JSONL'
{"id":"doc-1","category":"database","metadata":{"reviewed":true}}
{"id":"doc-2","category":"developer-tools"}
JSONL

lambdadb docs update --collection cli-demo-docs --branch main --file updates.jsonl --json
```

`docs delete` takes exactly one selector: `--ids`, or a `--file` with `ids` or a `filter` in the query DSL plus an optional `partitionFilter`. Deletion runs without confirmation and is reported as accepted; deleted documents can remain visible until the write commits. Preview a filter with `docs list --file` using the same `filter` first.

```bash
lambdadb docs delete --collection cli-demo-docs --branch main --ids doc-2 --json

cat > delete-filter.json <<'JSON'
{ "filter": { "queryString": { "query": "category:developer-tools" } } }
JSON

lambdadb docs delete --collection cli-demo-docs --branch main --file delete-filter.json --json
```

## Manage collections

List collections with `lambdadb collections list --json`. One page is returned by default; use `--page-token` with the returned `nextPageToken`, or `--all` to fetch all pages within the network budget.

`collections create` also accepts `--description`, repeated `--tag KEY=VALUE` metadata tags, `--partition-config` with a JSON object, and `--snapshot-retention-days`. `collections update` takes any combination of `--index-config`, `--description` (`""` clears it), `--tag` or `--clear-tags` (replacing the whole tag map), and `--snapshot-retention-days`, following the [collection update rules](/guides/collections/manage-collections#configure-a-collection):

```bash
lambdadb collections update --collection cli-demo-docs --description "Support articles" --tag team=search --json
lambdadb collections update --collection cli-demo-docs --index-config index-config.json --json
```

## Branches, tags, and aliases

The `branches`, `tags`, and `aliases` commands manage [data versioning refs](/guides/data-versioning/branches-tags-aliases). Sources and targets use the same `kind:NAME` form as `--ref`:

```bash
lambdadb branches list --collection cli-demo-docs --json
lambdadb branches create --collection cli-demo-docs --branch candidate --json
lambdadb branches create --collection cli-demo-docs --branch replay --source branch:main --as-of 2026-10-01T00:00:00Z --json
lambdadb tags create --collection cli-demo-docs --tag release-one --source branch:candidate --json
lambdadb aliases create --collection cli-demo-docs --alias production --target tag:release-one --json
lambdadb aliases retarget --collection cli-demo-docs --alias production --target branch:main --json
lambdadb aliases delete --collection cli-demo-docs --alias production --json
lambdadb tags delete --collection cli-demo-docs --tag release-one --json
lambdadb branches delete --collection cli-demo-docs --branch candidate --json
```

`branches create` copies the committed state of a branch (`--source branch:NAME`, default `main`); `tags create` pins the committed snapshot of a branch or tag. Pending writes are not included in either. `--as-of` takes Unix epoch milliseconds or an ISO 8601 time and applies to branch sources only. Aliases are read names for a branch or tag, never write targets or targets of other aliases, and `retarget` changes what every reader of the alias sees immediately.

Deletes take effect without confirmation. The server refuses to delete `main` and refuses to delete a branch or tag while an alias references it (HTTP `409`); list aliases, then retarget or delete them first. Mutations are never retried; an unverifiable outcome exits with code `5`, so list the refs before retrying.

### Clean up the example collection

After completing the examples, use `collections delete` to permanently remove the collection with all documents, branches, tags, and aliases, without confirmation:

```bash
lambdadb collections delete --collection cli-demo-docs --json
```

## Configuration and credentials

The default config path is `${XDG_CONFIG_HOME:-$HOME/.config}/lambdadb/config.json`. It is user-local, not discovered from the working repository. The CLI does not load `.env` files.

| Setting | Precedence, highest first |
|:--------|:--------------------------|
| Endpoint | `--endpoint`, `LAMBDADB_ENDPOINT`, saved `endpoint` |
| Project | `--project`, `LAMBDADB_PROJECT`, saved `project` |
| Key variable name | `--api-key-env`, `LAMBDADB_API_KEY_ENV`, saved `apiKeyEnv`, default `LAMBDADB_API_KEY` |
| Key value | Explicit `--api-key-env` or `LAMBDADB_API_KEY_ENV` selects environment mode; otherwise use the saved OS credential reference when present, else the selected variable. An explicit OS reference in generated agent arguments stays bound to its store. No automatic fallback on read failure |
| Config path | `--config`, `LAMBDADB_CONFIG`, default user path |
| Network timeout | `--timeout-ms`, `LAMBDADB_TIMEOUT_MS`, default `30000` milliseconds |

Explicit empty values fail validation. Data commands fail if an explicitly selected config file is missing; `configure` and `init` can create it. `configure` uses the same precedence when saving settings. For a different secret variable, use `lambdadb configure --api-key-env MY_PROJECT_KEY`, then supply `MY_PROJECT_KEY` in the process environment. Setting only the key value in an environment variable does not override a saved OS credential reference.

No command accepts the raw API key as an argument. Config files are written atomically with mode `0600` on POSIX and contain connection settings and non-secret credential metadata, never the key value. Environment mode saves the variable name; account setup adds `credentialStore`, `credentialId`, `credentialKeyId`, and `credentialKeyName`. Avoid shell tracing around secrets. The active key is redacted from output, but document contents remain visible. SDK debug logging is disabled even if `LAMBDADB_DEBUG` is set.

## JSON output and failures

`--json` emits one object and a newline on stdout, including command failures. It uses `schemaVersion: 1`, `command`, `ok`, and optional `target`, `data`, and `error`. Diagnostics go to stderr. Help and version remain plain text. Invoke the executable directly for machine-readable output.

| Exit code | Meaning |
|:----------|:--------|
| `0` | Success, including empty results and write acceptance |
| `2` | Invalid input, file, request, configuration, or missing credentials |
| `3` | API/request failure, or import with no accepted or unknown batches |
| `4` | Partial import: some accepted records, no unknown outcomes |
| `5` | At least one write outcome is unknown; inspect before retrying |

Import and update report `accepted`, `failed`, `unknown`, and `notAttempted` counts plus batch line ranges. A timeout or disconnect after dispatch can mean an unknown outcome. There are no automatic write retries, durable checkpoints, or resume support in the general CLI. Inspect the target and report before constructing a retry.

The shared network budget covers retries, pages, batches, and large-result downloads. Use `--timeout-ms 120000` for a longer operation. Optional `--mode bulk` uses bulk ingestion, which never generates native embeddings; a record with a present source must supply its native vector directly. See [Bulk upsert data](/guides/documents/bulk-upsert-data).
